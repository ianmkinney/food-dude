AmpliFood architecture

Last updated October 10, 2026 (assistant: Ampi; voice: on-device TTS/STT only at launch) · github.com/ianmkinney/food-dude

AmpliFood is a recipe and kitchen app (recipes, meal planner, pantry, grocery list, AI Chef, and Ampi — pronounced AM-pee) built once with React Native and Expo for iOS, Android and the web. Everything the user creates lives on their device in SQLite. AI features work with bring-your-own-key today; AmpliFood Plus and credit packs are in the app, with platform AI routed through a stub until the backend ships. Ampi is the chat-first home tab with tool calls and on-device voice only at launch (no cloud TTS). Click or focus any box to read what it does.

Trust boundaries & privacy

Inside the device boundary

  • All user data is local: recipes, plans, pantry, grocery, parties, chat history and profile in SQLite.
  • AI keys live in the iOS Keychain or Android Keystore (SecureStore). On web, keys are in localStorage and the database is in the browser's Origin Private File System (OPFS).
  • Theme and UI preferences are in AsyncStorage.
  • Camera is used only for barcode scanning; only photos the user picks are read.

What crosses the boundary today

  • AI requests go directly from the device to Anthropic, OpenAI, xAI or Google with the user's own key. AmpliFood never sees them.
  • Barcode numbers (only the number) go to Open Food Facts.
  • Recipe import fetches the page the user supplied; the text is then sent to the chosen AI provider.
  • Vercel serves static files only. There is no AmpliFood backend and no user data on the server.

What changes with platform AI (planned)

  • Prompts for Plus and credit users go through the AmpliFood AI proxy, which can read them in transit.
  • AmpliFood's provider key stays server-side only and never ships in the app.
  • Identity is an anonymous install ID (passed as appAccountToken / obfuscatedAccountId), not an email or name.
  • The server keeps a credit ledger (grants, debits, refunds) and validates store receipts.
  • Bring-your-own-key stays available and unchanged.

Ampi voice (at launch)

  • Text-to-speech: the phone's own voice only (expo-speech / OS TTS). Free, no API key, no audio leaves the device for TTS.
  • Speech-to-text: on-device where the OS allows (iOS Speech, Android SpeechRecognizer, Web Speech API — some browsers may use a vendor cloud).
  • Captions, mute, and auto-off while a screen reader is on for every spoken reply.
  • The microphone is requested only when the user taps talk.
  • Not at launch: hosted premium voices (e.g. ElevenLabs). That path is future work pending commercial approval; there is no Premium Sous voice and no voice proxy in production.

Open questions

  • Which host for the platform-AI backend (Vercel Functions, a small container service, or a managed BaaS), and which database for the ledger?
  • If we add a hosted premium voice later (e.g. ElevenLabs), what cap and pricing model fits Plus and credit packs?
  • Speech-to-text on the web: Web Speech API is missing or cloud-backed in some browsers. Is a typed fallback enough?
  • How do we restore credits if a user reinstalls (anonymous install ID is lost)?
